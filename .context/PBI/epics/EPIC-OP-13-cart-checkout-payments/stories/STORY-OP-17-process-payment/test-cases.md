## 🚨 Paso 2: Story Quality Analysis

### Ambiguities Identified

**Ambiguity 1:** "Payment token/details" transfer
- **Location in Story:** Technical Notes
- **Question for Dev:** Are we using a "One-time Token" (Stripe style) or sending card data?
- **Impact on Testing:** Crucial for security and payload verification.
- **Suggested Clarification:** Use only Secure Tokens generated by the Gateway SDK. Never touch raw card data in OnePets server.

**Ambiguity 2:** Order status on creation
- **Location in Story:** Scenario 1
- **Question for PO:** Should it be "PENDING" or "PAID"? 
- **Impact on Testing:** DB verification.
- **Suggested Clarification:** Status should be "PAID" if gateway confirms success.

### Edge Cases NOT Covered in Original Story

**Edge Case 1:** Webhook/Callback Failure
- **Scenario:** Payment is successful at gateway, but user closes browser before redirect to confirm.
- **Expected Behavior:** Backend should receive a Webhook from gateway to create the order asynchronously.
- **Criticality:** Critical
- **Action Required:** Add test case for Webhook processing.

**Edge Case 2:** Race Condition on Stock
- **Scenario:** Stock is 1. Two users pay at the exact same time.
- **Expected Behavior:** One should fail gracefully. Rollback payment if stock is gone.
- **Criticality:** High
- **Action Required:** Integration test for stock depletion during order creation.

## ✅ Paso 3: Refined Acceptance Criteria

### Scenario 1: Payment Success (Happy Path)
**Type:** Positive
**Priority:** Critical

- **Given:** Cart total is $55.00. Payment method is "Credit Card".
- **When:** User submits valid card details and clicks "Pay".
- **Then:**
  - Gateway returns `status: success`.
  - API creates order in `public.orders` with `total: 55.00`, `status: paid`.
  - `public.cart_items` for user is deleted.
  - UI redirects to Order Confirmation page.

### Scenario 2: Card Declined
**Type:** Negative
**Priority:** High

- **Given:** User uses a card with insufficient funds.
- **When:** User clicks "Pay".
- **Then:**
  - Gateway returns `error: insufficient_funds`.
  - UI shows "Payment failed: Insufficient funds".
  - NO order is created in DB.
  - Cart items remain intact.

### Scenario 3: Gateway Timeout
**Type:** Negative/Edge Case
**Priority:** Medium

- **Given:** Gateway takes > 30s to respond.
- **When:** User clicks "Pay".
- **Then:** UI shows "Processing taking longer than usual... please check your email". No double charge allowed.

## 🧪 Paso 4: Test Design

### Test Outlines

#### **Validar pago exitoso y creación de orden**
**Type:** Positive
**Priority:** Critical
**Test Level:** E2E / Sandbox

**Preconditions:**
- Mock Payment Gateway in "Success" mode.

**Test Steps:**
1. Complete Checkout flow.
2. Submit payment.
3. Check Order ID in URL.

**Expected Result:**
- **DB:** `orders` table has new row. `stock` decreased for items.

---

#### **Validar rechazo de pago**
**Type:** Negative
**Priority:** High
**Test Level:** Integration

**Preconditions:**
- Mock Gateway in "Declined" mode.

**Test Steps:**
1. Try `POST /api/orders` with declined token.

**Expected Result:**
- **Status:** 402 Payment Required or 400.
- **Body:** `{ "error": "PAYMENT_DECLINED" }`.

---

#### **Validar Webhook de confirmación (Asíncrono)**
**Type:** Integration
**Priority:** Critical
**Test Level:** Backend

**Test Steps:**
1. Send mock Webhook from Gateway to `/api/webhooks/payment` with `type: charge.succeeded`.

**Expected Result:**
- **DB:** Order created even without user browser interaction.
